# 서론·결론 스토리와 전체 한계

최종 발표의 서론·결론 흐름과 프로젝트 전체 한계를 정리한다. 모듈별 수치의 근거는 동적 검증 `docs/eval-results.md`(#88), 정적 검토량 `docs/validator-review-workload.md`, 배치 결과 #72·#80·#95 이다. 이 문서의 수치는 모두 그 결과 파일(`eval/results/`)에서 다시 낸 실측값이다. 시뮬레이터 예상은 따로 표시한다.

## 기준

- 결과: 본 실험 1차(#72, 실행 커밋 `672a8a0`, 309회), 2라운드 배치(#80, 실행 커밋 `910dc8e`, 21회), 프로브 v2 배치(#95, 실행 커밋 `8f7e037`, 156회: 정답 21·오류 주입 60·LLM 후보 75, 각 1회). aborted 는 모두 0회다.
- 아래 표와 수치는 특별히 적지 않으면 v1 프로브만 있던 1차·2라운드 배치 기준이다. 프로브 v2 배치 결과는 "프로브 v2 배치" 절에 따로 적는다.
- 시나리오: 배치는 req-001 ~ 021 의 21개로 돌았다. req-022(hping3, #87)는 배치에 들어 있지 않다.
- LLM 후보: `qwen2.5:14b`(digest `7cdf5a0187d5`), Ollama 0.40.3, 프롬프트 v2, temperature 0.7, seed 1·2·3. 1라운드 63개(21개 시나리오 × 3), 2라운드 12개.

## 서론

1. **문제**: 자연어 요구사항으로 LLM 이 방화벽 룰을 만들면, 문법은 맞지만 포트·범위·순서가 틀린 룰이 나올 수 있다. 방화벽 오류는 장애(정상 통신 차단)나 사고(공격 허용)로 바로 이어진다.
2. **기존 접근**: 룰 파일만 읽는 정적 검증(문법, 범위, 룰끼리의 충돌)은 선행연구와 도구가 있다 (`docs/related-tools.md`). 룰 목록이 정답과 같아도 실제 동작이 다른 경우(예: 응답 트래픽 누락)는 정적 검증으로 보이지 않는다.
3. **연구 질문**
   - RQ1. 정적 검증을 통과한 AI 방화벽 룰 중 **동적 검증만 잡아내는 오류**는 얼마나 되고 어떤 유형인가?
   - RQ2. 위험도 기반 선별 적용으로 **사람 검토량을 얼마나 줄이면서** 안전성을 유지할 수 있는가?
4. **접근**: 생성 → 정적 검증·위험도 판정 → (고위험만 사람 승인) → 격리 랩 적용 → 정상·공격 프로브로 감시 → 실패 시 자동 롤백. 그리고 실패 내용을 생성기에 돌려주는 2라운드 재생성.
5. **기여**
   - Podman 격리 랩에서 실제 패킷으로 AI 룰을 검증하고 자동 롤백하는 파이프라인
   - 21개 시나리오(정답 룰셋·프로브)와 12개 유형 오류 주입 60개로 된 평가 세트
   - "관측하지 못했으면 결과를 내지 않는다"는 측정 원칙 (`AGENTS.md`). 330회 실행이 모두 관측된 결과로 남았다 (aborted 0)

## 결론

### RQ1. 동적 검증만 잡는 오류

**오류 주입 (60개 × 3회)**

| 구분 | 오류 주입 수 | 내용 |
| --- | ---: | --- |
| 정적 검증이 잡음 (고위험, 승인 거부) | 16 | order 4, action 3, proto 3, widen 3, port-any 2, extra 1 |
| 동적 검증만 잡음 (저위험, 롤백) | 44 | state 21, missing 4, port 4, widen 4, narrow 3, range 3, swap 2, action 1, extra 1, proto 1 |
| 둘 다 놓침 | 0 | |

- 동적 추가 탐지율은 1.0 이다. 다만 오류 주입은 시나리오 프로브로 드러나게 만든 것이라 **예상된 값**이다(#50). 파이프라인이 의도대로 동작한다는 확인으로 본다.
- 의미 있는 결과는 **state 유형 21개**다. 상태 추적 룰을 빼면 IR(룰 목록)은 정답과 똑같아서, 정적 검증과 IR 시뮬레이터 모두 정답으로 본다. 랩에 실제로 적용해야만 응답 패킷이 막혀 정상 통신이 실패하는 것이 보인다.

**실제 LLM 후보 (1라운드 63개)**

| 결과 | 수 | 정답과 같은 정책 |
| --- | ---: | ---: |
| 고위험 → 승인 거부 | 9 | 0 |
| 저위험 → 적용 → 롤백 (동적 검증만 잡음) | 3 | 0 |
| 저위험 → 적용 유지 | 51 | 48 |

- 정적 검증을 통과한 54개 중 정답과 정책이 다른 것은 6개였다. 그중 동적 검증이 3개를 잡았다(req-017 s1·s2·s3). **오류 주입이 아닌 실제 LLM 출력의 오류를 동적 검증만 잡은 사례**다. 요구사항의 "8000-8100 허용, 단 8080 제외"를 한 범위로 쓰거나 일부 허용을 빠뜨렸다.
- 나머지 3개는 모든 프로브를 통과해 적용된 채 남았다.
  - req-013 s1·s2: IoT 망 허용을 IoT 기기 한 대로 좁혔다(과차단). 프로브가 그 한 대에서만 나가서 드러나지 않았다. 결과를 본 뒤 추가한 프로브 v2(#85)로 다시 돌린 배치(#95)에서는 v2 프로브 n-004(같은 IoT 망의 attacker 출발) 실패로 롤백됐다.
  - req-019 s2: 목적지를 서버 한 대 대신 서버 망 전체로 넓혔다(과허용 18). 랩의 서버 망에 호스트가 한 대뿐이라 **어떤 랩 프로브로도 드러나지 않는다**.
- 표본이 작다. 동적 검증만 잡은 3개는 모두 같은 시나리오(req-017)에서 나왔다. 비율로 일반화하지 않고 "이런 유형이 실제로 나온다"는 사례로 제시한다.

### RQ2. 위험도 기반 선별 적용

- 1라운드 63개 중 사람 승인이 필요한 고위험은 9개였다. 검토 대상 파일은 63 → 9 (85.7% 감소), IR 룰은 216 → 40 (81.5% 감소)이다 (`docs/validator-review-workload.md`). 정적 집계이고, 사람이 실제로 검토한 시간을 잰 것은 아니다.
- 고위험 9개는 모두 정답과 정책이 달랐다. 승인 거부로 적용을 막은 것이 맞았다.
- 저위험으로 사람 검토 없이 적용된 54개 중 정책이 틀린 3개는 동적 검증이 롤백했다. 감지 시간은 평균 41.7초, 복구 시간은 평균 0.397초였다.
- **남은 위험**: 저위험이면서 동적 검증도 통과한 정책 차이 3개가 적용된 채 남았다. 특히 req-019 s2 는 과허용이다. 랩에서는 넓어진 범위에 호스트가 없어 아무 일도 없지만, 호스트가 더 있는 실제 망이라면 의도하지 않은 접근을 허용한다. "사람 검토를 줄여도 안전하다"는 결론은 **랩 프로브가 다루는 범위 안에서만** 성립한다. v2 배치(#95)에서는 이 3개 중 req-013 s1·s2 가 롤백되어 req-019 s2 하나만 남았다.

### 피드백 재생성 (2라운드 12개)

1라운드에서 승인 거부되거나 롤백된 후보에 실패 내용을 주고 다시 생성했다.

| 1라운드 실패 단계 | 후보 | 2라운드: 적용·정답과 같음 | 적용·정답과 다름 | 여전히 실패 |
| --- | ---: | ---: | ---: | ---: |
| 승인 거부 (고위험 이유를 피드백) | 9 | 5 | 1 | 3 (고위험) |
| 롤백 (실패한 통신을 피드백) | 3 | 0 | 0 | 3 (롤백 1, 스키마 위반 2) |

- 고위험 이유를 준 9개 중 5개는 정답과 같은 정책이 되었다. 프로브만 맞춘 것이 아니라 정책이 같아졌으므로, 같은 프로브로 채점하는 문제(#45)는 이 5개에 해당하지 않는다.
- 남은 1개(req-006 s3 r2)는 고위험은 벗어났지만 IoT 망 허용을 한 대로 좁혔다(과차단 3, 과허용 1). v2 배치(#95)에서 n-004 실패로 롤백됐다.
- 롤백 피드백 3개(req-017)는 하나도 고쳐지지 않았다. 범위를 쪼개야 하는 요구를 모델이 IR 로 옮기지 못했다.

### 프로브 v2 배치 (#95)

1차 결과에서 놓친 사례를 보고(#74) 망마다 다른 호스트에서도 보내는 프로브 35개를 `"set": "v2"` 로 더해(#85), 같은 후보를 한 번 더 돌렸다. v1 / v2 로 나눈 표는 VM 의 프로브 원본(`out/`)에 `eval/probe_sets.py`(#84)를 돌린 #95 본문의 값이다. 원본은 저장소에 없어서, `results.csv` 의 실행별 통과율과 시뮬레이터 판정(state 유형은 정상 통과율 0)으로 다시 맞춰 확인했다(#95 리뷰).

| 후보 | v1 정상 / 공격 | v2 정상 / 공격 | v1 은 통과하고 v2 에서만 실패 |
| --- | --- | --- | --- |
| 정답 (21회) | 55/55, 148/148 | 31/31, 4/4 | 없음 |
| 오류 주입 (60회) | 47/123, 313/323 | 28/71, 9/9 | 없음 |
| LLM 후보 (75회) | 157/163, 432/432 | 86/90, 13/13 | 3 (req-006 s3 r2, req-013 s1·s2, 모두 n-004) |

- 정답 21개가 v2 프로브를 모두 통과해, 더한 프로브가 정답과 어긋나지 않는다.
- 오류 주입은 v2 로 새로 잡힌 것이 없다. 오류 주입은 원래 v1 프로브로 드러나게 만든 것이라 예상과 같다. 정상 통과 수가 낮은 것은 state 유형 21개에서 정상 프로브가 모두 실패하기 때문이다.
- **1차·2라운드에서 모든 프로브를 통과했지만 정답과 달랐던 4개 중 3개가 v2 에서 롤백됐다.** 남은 req-019 s2 는 랩 구성 때문에 v2 로도 드러나지 않는다.
- v2 프로브는 2라운드 피드백에 쓰이지 않았으므로 2라운드 후보의 hold-out 채점이 된다. 배포까지 가서 v1 을 모두 통과한 2라운드 후보 6개 중 v2 에서 실패한 것은 req-006 s3 r2 하나다. 나머지 5개는 hold-out 프로브도 통과했다.
- 이 결과는 #85 의 시뮬레이터 예상과 같다. 세 후보는 Mac 랩에서도 같은 결과(v1 전부 통과, v2 n-004 실패로 롤백)를 확인했다(#95 리뷰).
- v2 프로브가 분모에 들어가므로, 이 배치의 정상 통과율을 1차와 그대로 비교하지 않는다 (예: req-017 s1 이 5/7 → 8/10).

### 한 문장 결론

> 정적 검증은 룰 목록에서 보이는 오류(순서·범위·동작)를 걸러 사람 검토 대상을 63개 중 9개로 줄였고, 동적 검증은 룰 목록으로는 보이지 않는 오류(응답 트래픽 누락, 실제 LLM 의 범위 오류)를 롤백으로 막았다. 다만 랩 프로브가 닿지 않는 정책 차이는 둘 다 놓친다.

## 전체 한계

모듈별 한계는 `docs/eval-results.md`(동적), `docs/validator-review-workload.md`(정적)에 있다. 여기서는 생성·시나리오 쪽과 전체에 걸친 것을 적는다.

1. **모델 하나, 로컬 14B 만 썼다.** `qwen2.5:14b` 하나를 temperature 0.7, seed 3개로 돌렸다. 상용 모델이나 다른 크기의 모델에 그대로 일반화할 수 없다 (#21). 계획했던 7B 비교는 하지 못했다.
2. **시나리오가 한 사람, 한 토폴로지에서 나왔다.** 요구사항·정답 룰셋·프로브·오류 주입을 같은 사람(시나리오 담당)이 만들었고, 랩은 스마트홈 4개 망·6개 호스트 하나다. 요구사항 해석과 "정답"이 그 기준을 따른다. 실제 기업망 규모의 룰셋(수백 개 룰)은 다루지 않았다. 정답 룰셋은 시나리오당 1 ~ 8개(평균 2.9개)다.
3. **실제 LLM 오류 표본이 작다.** 정적 검증을 통과한 정책 차이는 63개 중 6개, 시나리오로는 3개(req-013·017·019)다. 탐지 비율을 일반화할 수 있는 크기가 아니다.
4. **프로브 v2 는 결과를 본 뒤에 추가했다.** 1차 배치에서 놓친 사례(#74)를 보고 프로브를 보강했으므로, v2 로 잡히는 수는 사후 설계의 결과다. v2 배치(#95) 결과는 시뮬레이터 예상과 같았지만, 처음부터 그 프로브가 있었다고 볼 수는 없다. 오류 유형 목록은 첫 결과 뒤로 바꾸지 않았다 (`AGENTS.md`).
5. **피드백 효과와 무작위성을 구분하지 못했다.** 2라운드는 피드백을 넣은 한 번의 재생성뿐이고, 피드백 없이 같은 조건으로 다시 생성한 대조군이 없다. 대화 내용이 달라 같은 seed 라도 출력이 달라지므로, 5개가 고쳐진 것이 피드백 덕분인지 다시 뽑아서인지 이 결과만으로 가를 수 없다. 라운드도 1회다.
6. **랩 구성으로 볼 수 없는 차이가 있다.** 배치에 쓴 21개 시나리오의 변형 630개 중 17개는 어떤 랩 프로브로도 드러나지 않는다 (`scenarios/coverage.py`. req-022 를 포함한 현재 main 22개 기준으로는 672개 중 19개). 실제 LLM 후보 req-019 s2 가 여기에 해당한다. 호스트를 늘리면 줄일 수 있지만 랩이 커진다.
7. **"고위험"은 정답 라벨이 아니다.** 위험도는 범위·충돌 규칙으로 정한 것이다. 이번에는 고위험 9개가 모두 실제로 정답과 달랐지만, 고위험인데 정답과 같은 정책인 경우도 있다(`docs/validator-week2-hypothesis-design.md` 의 req-010 v1 사례).
8. **공격 프로브가 단순하다.** nmap 연결(connect) 스캔, hping3 SYN 1개(req-022, 배치에는 없음), TCP·UDP 연결 시도와 ICMP(ping)다. 상태 추적을 우회하는 ACK·FIN 같은 공격은 다루지 않았다.

## 향후 과제

- req-022(hping3)를 포함한 배치로 정답·오류 주입·LLM 후보 결과 얻기
- 피드백 없이 다시 생성한 대조군으로 피드백 효과를 분리하기
- 다른 크기·종류의 모델로 같은 시나리오 생성하기
- 호스트를 늘린 랩으로 관측 불가 차이 줄이기
