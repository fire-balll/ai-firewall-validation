## 1. 이번 주에 정리한 결론

기존 오류 주입 16개를 최신 main의 실제 validator와 시뮬레이터로 다시 실행했습니다. 모두 형식 검사를 통과했고, 전체 위험도는 high 7개·low 9개입니다. 두 order 파일의 문서상 low를 high로 정정해야 하며, req-010-extra의 실패 프로브에는 a-011도 포함됩니다.

기존 룰셋 검사는 ‘동시 적용 충돌’보다 ‘전체 교체 전후 정책 변화’를 기본으로 설계하는 것을 권고합니다. 현재 변환기는 flush ruleset으로 시작하는 완전한 새 룰셋을 만들고 deployer가 이를 적용합니다. 기존 룰과 신규 룰을 이어 붙이면 실제 적용하지 않는 정책을 검사하게 됩니다.

쉽게 말하면, 이전 출입 안내문을 새 안내문으로 통째로 바꾸기 전에 ‘누가 새로 들어갈 수 있고 누가 더 이상 못 들어가는가’를 비교하는 일입니다. 안내문 두 장을 동시에 붙여 놓고 모순을 찾는 방식은 현재 운영 방식과 다릅니다.

정적 high는 사람이 내용을 검토해야 한다는 뜻입니다. 실제 요구와 다른 정책인지는 별도 비교가 필요합니다. low 역시 요구 충족이나 안전을 보증하지 않습니다. 동적 실패는 실제 랩에서 기대와 다른 통신이 관측된 경우이며, 이번 시뮬레이션 실패와 구분해 기록합니다.

## 3. 가설 설명에서 반드시 분리할 사례

state 10개(req-001~010): JSON은 각 gold와 같고 시뮬레이터의 실패 프로브도 없습니다. 하지만 정확한 파일명 req-NNN-state-NN.json을 stateful_for에 넣으면 stateful=False가 됩니다. 변환 결과에서 ct state established,related accept가 빠지는 것을 확인했습니다. 응답·연결 성립을 이번 도구로 측정하지 않았으므로 state_pending_lab로 두고 equivalent나 동적 탐지 성공으로 집계하지 않습니다.

req-011 widen:g-001.src->any: 룰 쌍은 redundancy/low지만 전체 risk는 high입니다. 넓은 accept 범위 이유가 따로 생기며 guest a-001이 시뮬레이터에서 실패합니다. 정적 검사에서 표시되지 않는 오류의 예시는 아닙니다.

req-011 missing:g-002: 전체 risk=low, 정적 이상·high 이유 없음, 정상 IoT n-002 실패입니다. 정적 경고 없이 요구가 틀리는 예시로 적절합니다. 실제 ‘동적만 추가 탐지’ 수치는 해당 변형의 랩 기록이 있어야 채웁니다.

high이지만 동등한 반례: v1 req-010-qwen2.5-14b-s1.json은 high지만 정답과 초기 패킷 판정이 같습니다. 뒤의 불필요한 룰이 경고를 만들더라도 정답과 다른 동작이라는 뜻은 아닙니다. PR35의 v2 동명 파일은 다른 입력이므로 이 결론을 옮기지 않습니다.

PR36 coverage의 missed 5개는 req-012의 drop 관련 3개와 req-014의 drop 관련 2개입니다. 이번 재실행에서도 656개 경계 등가영역 전체에서 정답과 차이 0입니다. coverage는 일부 순서변형만 equivalent로 선별해 나머지를 missed에 넣을 수 있으므로, 이 5개를 랩 부족으로 놓친 오류라 해석하면 안 됩니다.

| 시나리오 | 정상 순서 | priority 역전 | 실패 프로브 |
|---|---|---|---|
| req-012 | generalization / low | shadowing / high | n-001: 허용 웹 차단 |
| req-014 | generalization / low | shadowing / high | a-001: 8080 과허용 |

이상의 동등성은 IPv4·연결 시작 패킷·first-match/default-drop IR에 한정됩니다. 응답, conntrack, NAT, 서비스 동작 및 실제 커널 규칙의 동등성을 뜻하지 않습니다.

## 4. 기존 룰셋 검사의 권고 입력과 목적

목적: 적용 중인 관리 대상 정책을 신규 완전 룰셋으로 교체할 때, 허용→차단과 차단→허용의 변화 및 그 근거를 사람이 확인할 수 있게 합니다. 이전 정책과 다르다는 이유만으로 오류로 확정하지 않고, 요구사항·승인된 변경·정상/공격 프로브와 연결합니다.

‘기존 룰셋’은 임의의 gold가 아니라 적용 직전에 fw에서 읽은 실제 상태와 연결된 관리 대상 IR입니다. 신뢰 가능한 이전 IR이 없고 nft 스냅샷만 있으면 지원 밖/확인 불가로 보고합니다. nft 원문을 임의로 IR로 역변환하거나 빈 룰셋으로 채우지 않습니다.

입력 권고: 기존 schema/rule.schema.json을 바꾸지 않고, 별도 비교 요청 파일을 사용합니다. 두 IR과 원본 경로·해시·상태 추적 모드·적용 위치를 함께 묶습니다. 실제 상태 수집은 통합 담당 경로에 연결하고, validator가 임의로 방화벽 상태를 수정하지 않습니다.

| 입력 | 필수 내용 |
|---|---|
| baseline | 기존 IR 경로·SHA-256·원본 파일명, stateful, 적용 커밋·대상 fw 식별자 |
| snapshot | 실제 nft 원문 보관 경로·SHA-256·수집 시각·관리 대상 검증 기록; 실행 시 변하는 counter와 정책 구조는 구분 |
| candidate | 신규 완전 IR 경로·SHA-256·원본 파일명·stateful; 적용 모드는 파일명에서 결정한 값을 그대로 기록 |
| context | replace 모드, table inet fwlab / forward, hook priority 0, default drop, IPv4 범위 |
| requirements | scenario 경로·SHA-256, 정상/공격 probes, 승인된 의도 변경의 근거 ID; 없으면 정책 변화만 보고 |
| provenance | 변환기 커밋·기존 IR과 snapshot 연결 근거. 실제 상태가 달라졌으면 stale_baseline으로 수집부터 다시 수행 |

교체 직전 동일성 확인은 파일 바이트 비교만으로 끝내지 않습니다. nft 카운터·핸들처럼 실행 중 바뀌는 값과 정책 구조를 분리해 관리 IR과 실제 상태의 연결을 확인해야 합니다. 신뢰 가능한 연결이 없으면 비교 완료로 내지 않는 설계입니다.

권고 출력은 comparison 별도 보고서입니다: status(completed/indeterminate/out_of_scope), mode, 입력 해시, 지원 범위, 변경 영역·대표 패킷, 변경 전후 결정 룰, 정책 차이 분류, 모드 차이, 요구와의 대응. 기존 validate의 ok/risk/errors 계약은 유지합니다.

## 5. 비교 경계와 3주차 구현 수용 기준

기본 알고리즘 권고: 두 룰셋을 각각 유효성 검사하고 priority·id 순으로 독립 평가합니다. 주소 CIDR 경계와 포트 구간 경계를 합쳐 같은 판정이 유지되는 영역을 만들고, 영역별 before/after를 비교합니다. 같으면 equivalent, 다르면 allow→block 또는 block→allow로 분류하고 대표 패킷·결정 룰을 남깁니다. 경계영역 수는 실제 트래픽 비율이 아닙니다.

변경 검출과 오류 판정을 분리합니다. 승인된 포트 변경처럼 의도한 차이는 변경 목록에 남기되 오류로 부르지 않습니다. 정상/공격 프로브의 기대와 어긋나는 경우는 requirement_mismatch로 연결합니다. 요구 원문이 없으면 safety를 확정하지 않고 policy_delta만 보고합니다.

동시 적용 모드는 기본 입력으로 받지 않는 것을 권고합니다. 향후 append·부분 교체·다중 체인 적용으로 바뀌면 실제 테이블/체인, hook 우선순위, jump/goto, 정책, 룰 삽입 위치를 먼저 정의한 별도 모드가 필요합니다. 서로 다른 체인의 accept를 단일 first-match accept로 합치는 방식은 사용하지 않습니다.

stateful가 다르면 같은 JSON이라도 동등으로 결론내리지 않습니다. 상태 추적, 기존 연결 잔존, 응답, NAT, set/map, IPv6, 다중 hook 및 다른 테이블은 초기 구현 지원 범위 밖입니다. snapshot에 지원 밖 요소가 있으면 전체 방화벽이 안전하다고 판정하지 않습니다. flush ruleset은 다른 테이블도 제거하므로, 관리 정책 외 규칙이 존재하면 적용 전 통합 담당 확인이 필요합니다.

중복 id·동일 priority는 원본을 덮어 합치지 않습니다. 비교 키는 before/after 구분+원본 순번+id로 보존하고, 실제 정렬 규칙을 그대로 적용합니다. 모호한 중복 식별자는 입력 진단으로 남겨 팀 규약에 따라 정리합니다. 임의 id 변경은 같은 priority의 동작을 바꿀 수 있습니다.

현재 실행한 design-seeds는 설계 검증용 입력입니다. 기존 simulator를 각각 실행해 변화 유무를 확인한 것이며, validator의 기존 룰셋 충돌 TODO를 구현하거나 배포 경로에 연결한 것은 아닙니다.

| 수용 기준 | 3주차에 확인할 결과 |
|---|---|
| 실행 실패 | 파일 없음·파싱 실패·도구 실패는 비0 종료와 원인. 비교 성공·안전 판정으로 대체하지 않음 |
| 추적 가능성 | 두 입력 해시·커밋·모드·범위와 전후 결정 룰·대표 패킷을 연결 |
| 정책 변화 | 같은 정책·의도한 변경·과허용·과차단·지원 밖·상태 모드 차이를 별도 기록 |
| 기존 계약 | 단독 validate 출력과 위험도 의미 유지. comparison을 임의로 high/ok에 덮어쓰지 않음 |

## 6. 시험 시드와 팀에서 확인할 사항

설계 시드 D01~D07은 실제 기존 판정 함수와 독립 조건식으로 비교했습니다. 아래 나머지 항목은 통합 인터페이스가 구현된 뒤 수행할 수용 시험이며, 이번 실행 통과 수에 넣지 않았습니다.

| 시험 | 기대 결과 | 이번 상태 |
|---|---|---|
| D01 같은 정책 | 차이 0 | 실행 |
| D02 필요한 허용 삭제 | allow→block 변화 | 실행 |
| D03 포트 변경 | 과허용·과차단 변화 | 실행 |
| D04 승인된 포트 변경 | 차이는 유지, 의도 변경 근거와 연결 | 차이 실행; 승인 연동 후속 |
| D05 배열 나열 순서만 변경 | priority·id 정렬상 차이 0 | 실행 |
| D06·D07 예외 priority 역전 | 정책 차이·shadowing/high | 실행 |
| D08 nft만 있고 기존 IR 없음 | indeterminate | 후속 |
| D09 같은 JSON·stateful 다름 | 모드 차이, equivalent 금지 | 모드 함수 확인; 통합 후속 |
| D10 중복 id·동일 priority | 원본 보존·모호성 진단 | 후속 |

| D12 교체 직전 기준 변경 | stale_baseline, 재수집 | 후속 |

팀에 제시할 권고안: 기존 검사는 replace 전후 정책 변화 비교로 시작하고 동시 적용은 제외합니다. 입력은 관리 IR+실제 snapshot 연결 정보로 한정하며 비교 출력은 기존 risk와 분리합니다. 이 권고안을 기준으로 비교 범위와 통합 경로를 팀에서 검토합니다.

남은 팀 합의 1: replace 전후 비교를 기존 룰셋 검사 범위로 수용할지, snapshot 수집·기존 IR 보존/연결·최종 적용 직전 재확인을 어느 통합 경로에서 보장할지 확인합니다.

남은 팀 합의 2: 정책 변화의 사람 검토 처리, 승인된 변경 근거와 정상/공격 요구의 연결 방식, 관리 대상 밖 규칙이 있는 경우 적용 중단 기준을 함께 정합니다.

남은 팀 합의 3: mutations 문서 order 설명·두 risk 행 및 PR34 a-011 보완의 반영 경로, coverage missed 5개의 equivalent 표기, 동적 실패를 승인 가능한 high가 아닌 실패/롤백으로 정리하는 기록을 맞춥니다.

3주차 후속: 비교 인터페이스·실제 충돌 검사 구현과 통합시험, 실험 프로토콜 최신화·팀 공개입니다. 공동 선행연구 기록과 교수 AI 평가 기준 확인도 별도 공동 항목입니다. VM 실험·UDP/nmap·전체 배치 실행은 기존 담당 범위를 유지합니다.
