# 프로젝트 쉽게 보기

이 프로젝트를 처음 보는 사람(팀원, 발표 청중, 리뷰어)을 위한 안내서다. 자세한 규칙은 [`AGENTS.md`](../AGENTS.md), 모듈 구조는 [`README.md`](../README.md) 에 있다.

## 한 줄 요약

> **AI 가 만든 방화벽 룰을 그대로 믿지 않고, 격리된 실험실에 실제로 적용해 진짜 패킷을 보내 본 뒤, 안전한 것만 적용하고 문제가 생기면 자동으로 되돌린다.**

## 왜 이런 걸 하나

방화벽 룰은 "누가 누구에게 어떤 포트로 접속해도 되는가"를 정한 규칙 목록이다. 요즘은 사람이 자연어로 요구사항을 말하면 AI(LLM)가 룰을 만들어 준다.

> "PC 는 서버의 웹(80)에 접속할 수 있다. IoT 기기는 PC·서버에 먼저 접속할 수 없다."

문제는 AI 가 **그럴듯하지만 틀린 룰**을 만들 수 있다는 점이다. 포트를 잘못 쓰거나, 범위를 너무 넓게 잡거나, 룰 순서를 바꿔서 막아야 할 공격을 통과시킬 수 있다. 방화벽이 틀리면 장애(정상 통신 차단)나 보안 사고(공격 허용)로 바로 이어진다.

그래서 **AI 가 만든 룰을 자동으로 검사하는 파이프라인**을 만든다.

## 핵심 아이디어: 두 번 검사한다

| | 정적 검증 | 동적 검증 |
| --- | --- | --- |
| 비유 | 설계도를 눈으로 검토 | 실제로 지어 놓고 문을 두드려 봄 |
| 하는 일 | 룰 파일만 읽고 문법·범위·룰끼리 충돌을 찾는다 | 실험실 방화벽에 룰을 적용하고 정상·공격 패킷을 실제로 보낸다 |
| 담당 | `validator/` | `prober/`, `deployer/` |
| 못 잡는 것 | 룰 자체는 멀쩡한데 실제 동작이 다른 경우 | 실험실에 없는 호스트·경로로만 드러나는 오류 |

정적 검증은 이미 선행연구에 있다. 우리가 보고 싶은 것은 **"정적 검증을 통과했는데 동적 검증만 잡아내는 오류가 얼마나, 어떤 종류로 있는가"** 다 (연구 질문).

예를 들어 #23 에서 확인한 "응답 트래픽 누락"(상태 추적 룰이 빠짐)은 룰 목록만 보면 정답과 똑같다. 그런데 실제로 적용하면 응답 패킷이 막혀서 정상 통신이 전부 실패한다. 10개 시나리오 모두에서 정적 검증과 시뮬레이터는 통과했고, 실험실에서만 실패가 드러났다.

## 실험 무대: 스마트홈 망

IoT 기기(스마트 전구, 카메라 등) 하나가 해킹당했다고 가정하고, 그 기기가 집 안 PC·서버로 넘어가지 못하게 막는 상황이다. 모든 장비는 한 컴퓨터 안의 **Podman 컨테이너**이고, 외부 인터넷과는 끊겨 있다.

```
                       [ fw : 방화벽 (nftables) ]   <- AI 룰을 여기에 적용
                      /            |             \
   net-iot 10.10.10.0/24   net-lan 10.10.20.0/24   net-svc 10.10.30.0/24
     iot-dev  .10 (침해 가정)     pc .10               server .10 (웹 80, 8080)
     attacker .66 (공격 프로브)
```

fw 는 각 네트워크의 `.254` 주소를 갖는다 (`lab/topology.env`).

- 세 네트워크 사이를 오가는 트래픽은 **반드시 fw 를 지난다.** 정말 그런지 `lab/check-path.sh` 로 확인한다.
- 방화벽 기본값은 **default deny**: 허용 룰에 맞지 않으면 전부 막는다.

## 룰 하나가 거치는 과정

```
 ① 요구사항 ─▶ ② 생성 ─▶ ③ 정적 검증 ─┬─ 틀림 ──────────────▶ 반려 (적용 안 함)
                                     ├─ 고위험 ─▶ 사람 승인 ─┐
                                     └─ 저위험 ─────────────┤
                                                           ▼
                       ⑥ 기록 ◀─ 통과 ─ ⑤ 감시 (60초 프로브) ◀─ ④ 적용
                                         └─ 실패 ─▶ 자동 롤백 ─▶ ⑥ 기록
```

| 단계 | 하는 일 | 파일 | 결과물 |
| --- | --- | --- | --- |
| ① 요구사항 | 자연어 요구사항, 정답 룰셋, 확인할 패킷 목록(프로브)을 준비 | `scenarios/req-*.json` | 시나리오 |
| ② 생성 | LLM(로컬 Ollama)이 요구사항을 읽고 룰셋(IR JSON)을 만든다 | `generator/generate.py` | `candidate.json` |
| ③ 정적 검증 | 스키마·포트·`nft -c` 문법, 너무 넓은 허용, 룰끼리 충돌(이상 탐지 4종)을 본다 | `validator/validate.py` | `validation.json` (`ok`, `risk`) |
| ④ 적용 | 현재 방화벽 상태를 저장하고, 룰셋을 nftables 로 바꿔 한 번에(원자적으로) 적용 | `deployer/deploy.py`, `common/ir.py` | |
| ⑤ 감시 | 60초 동안 5초마다 정상·공격 프로브를 보낸다. 하나라도 기대와 다르면 저장해 둔 상태로 되돌린다 | `deployer/deploy.py`, `prober/probe.py` | `deploy.json` (`rolled_back`, `mttr_s`) |
| ⑥ 기록 | 통과율·차단율·롤백 여부·복구 시간을 CSV 한 줄로 남긴다 | `eval/evaluate.py` | `eval/results/results.csv` |

전체는 `pipeline/run.sh` 하나로 돈다.

```bash
./lab/up.sh                                   # 실험실 켜기
./lab/check-path.sh                           # 트래픽이 fw 를 지나는지 확인
./pipeline/run.sh scenarios/req-001.json      # 룰 하나를 끝까지
./lab/down.sh                                 # 실험실 끄기
```

### 모듈끼리 주고받는 것: IR

모든 모듈은 **같은 JSON 형식(IR, 중간표현)** 으로만 대화한다. 형식은 `schema/rule.schema.json` 이 정하고, 바꾸려면 팀 전원이 합의해야 한다.

```json
{
  "id": "g-001",
  "intent": "PC는 서버의 웹 서비스(80)에 접근할 수 있다",
  "src": "10.10.20.0/24",
  "dst": "10.10.30.10/32",
  "proto": "tcp",
  "dport": "80",
  "action": "accept",
  "priority": 100
}
```

변환기(`common/ir.py` 의 `to_nft`)가 이것을 실제 방화벽 설정으로 바꾼다. 응답 패킷을 통과시키는 상태 추적 룰은 변환기가 항상 맨 앞에 넣는다.

```
table inet fwlab {
  chain forward {
    type filter hook forward priority 0; policy drop;
    ct state established,related accept
    ip saddr 10.10.20.0/24 ip daddr 10.10.30.10/32 tcp dport 80 counter accept comment "g-001"
  }
}
```

### 프로브: "문 두드려 보기"

프로브는 "이 출발지에서 저 목적지 포트로 접속하면 통과해야 하나, 막혀야 하나"를 적은 것이다.

```json
{ "id": "a-001", "kind": "attack", "from": "iot-dev", "to": "10.10.30.10", "proto": "tcp", "port": 80, "expect": "block" }
```

`prober/probe.py` 가 해당 컨테이너 안에서 `nc`·`curl`·`nmap`·`ping` 을 실제로 실행하고 결과를 판정한다.

- 응답 없이 시간 초과 → 방화벽이 **막음** (block)
- 연결 성공, 또는 "Connection refused"(방화벽은 통과했고 서버 포트만 닫힘) → 방화벽이 **통과시킴** (allow)

### 위험도와 사람 승인

위험도는 AI 가 판단하지 않는다. 정해진 기준으로만 정한다 (`validator/README.md`).

| 판정 | 기준 예시 | 처리 |
| --- | --- | --- |
| 반려 | 스키마·문법 오류 | 적용하지 않는다 |
| 고위험 | `any` 나 /16 보다 넓은 범위를 허용, 모든 포트 허용, 룰끼리 충돌 | 사람이 승인해야 적용 |
| 저위험 | 그 밖 | 자동 적용 |

어느 쪽이든 적용된 뒤에는 똑같이 감시하고, 문제가 생기면 자동 롤백한다.

### 롤백

OPNsense 방화벽의 "적용 후 확정하지 않으면 자동 복원" 구조를 nftables 로 따라 만든 것이다.

1. 지금 방화벽 상태를 저장한다
2. 새 룰셋을 한 번에 적용한다 (실패하면 아무것도 바뀌지 않음)
3. 감시 기간 동안 프로브를 반복한다
4. 실패하면 저장해 둔 상태로 되돌리고, 감지부터 복원까지 걸린 시간(MTTR)을 기록한다

## 실험은 어떻게 하나

### 무엇을 검사하나: 후보 룰셋 세 종류

| 종류 | 위치 | 왜 |
| --- | --- | --- |
| 정답 (gold) | `scenarios/req-*.json` 의 `gold` | 파이프라인이 맞는 룰을 잘못 막지 않는지 확인 |
| 오류 주입 (mutations) | `mutations/` | 일부러 망가뜨린 룰. 생성기 품질과 상관없이 **검증기가 무엇을 잡는지** 잰다. 한 파일에 오류 하나만 넣는다 |
| LLM 생성 (generated) | `generated/` | 실제 AI 가 만든 룰. 각자 PC 에서 생성해 커밋하고, 생성 조건(모델·seed 등)을 `.meta.json` 에 남긴다 |

`pipeline/batch.py` 가 시나리오 × 후보 × 반복(3회)을 한꺼번에 돌리고, 실행 조건(커밋 해시 등)을 manifest 로 남긴다.

### 무엇을 비교하나

- **정적 단독 vs 정적 + 동적**: 같은 룰셋에 두 방식을 돌려, 동적 검증만 잡은 오류의 비율과 종류를 본다.
- **방식 B vs 방식 C**: B 는 AI 생성 + 사람이 전부 검토, C 는 AI 생성 + 자동 검증 + 고위험만 사람 검토. C 가 사람 검토량을 얼마나 줄이면서 안전한지 본다.

### 무엇을 재나

| 지표 | 뜻 |
| --- | --- |
| 동적 추가 탐지율 | 정적 검증을 통과한 오류 중 동적 검증만 잡은 비율 |
| 의미 일치율 | AI 룰셋이 정답 룰셋과 같은 판정을 내리는 비율 (문자열이 아니라 패킷 판정으로 비교) |
| 정상 통과율 | 허용돼야 할 통신 중 실제로 통과한 비율 (낮으면 과차단) |
| 공격 차단율 | 막혀야 할 통신 중 실제로 막힌 비율 (낮으면 과허용) |
| 위험 룰 탐지율 | 오류 주입 룰 중 검증 전체가 잡은 비율 |
| 사람 검토 룰 수 | B 는 전체, C 는 고위험 판정 수 |
| 롤백 MTTR | 이상 감지부터 복원 완료까지 시간 |

## 꼭 지키는 원칙: 관측하지 못했으면 결과를 내지 않는다

실험실 컨테이너가 꺼져 있거나 명령이 없어서 검사를 **못 한** 것을, "차단됨"·"반려됨" 같은 **결과처럼 기록하면 안 된다.** 이 프로젝트에서 실제로 여러 번 그런 버그가 있었다(#5, #7, #11).

- 검사를 못 하면 결과 JSON 대신 원인 메시지와 함께 **실패(종료 코드 ≠ 0)** 로 끝낸다.
- 파이프라인은 그 실행을 `aborted` 로 보고 결과 CSV 에 넣지 않는다. 대신 manifest 에 이유를 남기고, 결과를 보고할 때 aborted 수를 함께 적는다.
- 프로브 10개 중 9개만 돌았으면 그 실행 전체를 실패로 본다.

`pipeline/run.sh` 종료 코드:

| 코드 | 뜻 | CSV 기록 |
| --- | --- | --- |
| 0 | 적용 완료 (감시 통과 또는 롤백) | O |
| 3 | 정적 검증에서 반려 | O |
| 4 | 고위험인데 승인 거부 | O |
| 1 | 실행 실패 | X (manifest 에만) |

## 팀이 일하는 방식

1. 최신 `main` 에서 브랜치를 만든다: `feat/`, `fix/`, `docs/` 등 (`main` 에 직접 커밋하지 않는다)
2. 작게 커밋한다: `<type>(<모듈>): <무엇을 했는지>`
3. PR 전에 확인 명령을 돌리고 결과를 PR 본문에 적는다 (`AGENTS.md` "PR 생성 전 확인")
4. 다른 팀원 1명 이상이 승인하면 Squash and merge 한다
5. 외부(컨테이너·명령)에 의존하는 코드를 바꿨다면, 그 대상을 멈춘 상태에서 결과 대신 실패가 나는지 확인한다

| 담당 | 구간 | 디렉터리 |
| --- | --- | --- |
| 서진정 | 시나리오·정답·오류 주입·생성기 | `scenarios/`, `mutations/`, `generator/` |
| 양경찬 | 정적 검증·위험도 | `validator/` |
| 강윤서 | 동적 검증·평가 지표 | `prober/`, `eval/` |
| 정택준 | 실험실·적용·롤백·통합 | `lab/`, `deployer/`, `pipeline/`, `common/` |

## 용어

| 용어 | 뜻 |
| --- | --- |
| IR | 모듈끼리 주고받는 룰 JSON 형식 (`schema/rule.schema.json`) |
| nftables | 리눅스 방화벽. `nft` 명령으로 다룬다 |
| default deny | 허용 룰에 없는 트래픽은 전부 막는 기본 정책 |
| 상태 추적 (ct state) | 이미 허용된 연결의 응답 패킷을 자동으로 통과시키는 기능 |
| first-match | 위(priority 가 작은 것)부터 보고 처음 맞는 룰을 따른다 |
| 프로브 | 통과·차단을 확인하려고 실제로 보내는 접속 시도 |
| 오류 주입 | 정답 룰셋을 일부러 망가뜨려 검증기를 시험하는 것 |
| shadowing·correlation 등 | 룰끼리 겹쳐서 뒤 룰이 무시되거나 일부만 겹치는 이상 (`validator/README.md`) |
| 시뮬레이터 | 실험실 없이 룰셋 판정을 계산하는 도구 (`common/sim.py`). 실험실 결과와 비교해 차이를 찾는다 |
| 롤백·MTTR | 문제가 생긴 룰을 되돌리는 것, 그 복구에 걸린 시간 |
| aborted | 검사를 끝내지 못한 실행. 결과로 세지 않는다 |
